# Архитектура Sintence

Принятые решения вместе с причинами. Если решение мешает — правится этот файл,
а не обходится молча в коде.

## 1. Три источника данных, один интерфейс

У анализатора три источника, и они не похожи друг на друга:

| Источник | Где живёт | Когда доступен | Авторизация |
|---|---|---|---|
| **Match-V5** | удалённый HTTP Riot API | всегда, но с лимитами | dev/production-ключ |
| **Live Client Data API** | локальный `https://127.0.0.1:2999` | только пока идёт игра | не нужна |
| **LCU API** | локальный, неофициальный | пока запущен клиент | lockfile (порт + пароль) |

Match-V5 — история, удалённая и лимитированная. Live Client Data — реальное время,
локально и без ключа, но существует только во время матча. LCU — неофициальный API
клиента, аутентификация через lockfile, нужен для champion select.

**Все три стоят за одним интерфейсом типа `MatchSource`**, и ядро никогда не узнаёт,
с кем именно оно говорит. Это же даёт четвёртую реализацию бесплатно — источник из
фикстур для тестов.

Почему так: различия между источниками — это различия транспорта, а не предметной
области. Матч есть матч. Если транспорт протечёт в ядро, каждая новая интеграция
будет переписывать анализ.

## 2. Слои

```
core/      домен и больше ничего
data/      адаптеры источников (Match-V5, Live Client, LCU, фикстуры)
analysis/  метрики как чистые функции над типами core/
app/       CLI, HTTP-сервер, окно WebView2
web/       Vue-фронтенд, собирается Vite, в CMake не участвует
```

- **`core/`** — только доменные типы. Ни JSON, ни HTTP, ни файлов. Тестируется
  в изоляции, без сети и без диска.
- **`data/`** — адаптеры. Каждый умеет ровно одно: превратить чужой JSON в типы `core/`.
- **`analysis/`** — метрики, чистые функции: на входе типы `core/`, на выходе числа.
  Без ввода-вывода, поэтому тестируется таблицей значений.
- **`app/`** — точка входа, HTTP-сервер и окно. Здесь и только здесь живут
  cpp-httplib и WebView2.
- **`web/`** — фронтенд. Знает про HTTP и про JSON-схему ответов, и больше
  ни про что: ни одного пути к файлу, ни одного знания о том, где лежит кеш.

Зависимости идут только вниз: `app/ → analysis/ → core/`, `app/ → data/ → core/`.
`core/` не знает ни про кого. `web/` не знает даже про `app/` — только про
JSON-контракт.

## 3. Локальный кеш — источник истины

Приложение **всегда читает с диска**. Сеть и живая игра только наполняют кеш, но
никогда не отдают данные напрямую в анализ.

Из этого следует ровно то, что нужно:

- офлайн-режим получается сам собой, а не пристраивается потом;
- тесты не требуют сети;
- истёкший ключ ломает только докачку, а не работу приложения;
- лимиты Riot перестают быть проблемой интерактивного интерфейса.

## 4. Ни один тип фреймворка не попадает в `core/` и `analysis/`

Ни типов JSON-библиотеки, ни типов HTTP-клиента, ни типов HTTP-сервера. Только
`std::string`, `std::vector` и собственные доменные типы.

С веб-фронтендом это правило перестало держаться на дисциплине и стало
**физическим**. Через сокет тип не пролезет: граница между C++ и интерфейсом — текст JSON,
и она не умеет переносить типы.

Осталась одна лазейка, и проверять надо именно её: типы cpp-httplib и nlohmann
не должны выходить за пределы `app/` и `data/` соответственно.

## 5. Интерфейс: WebView2 + Vue в одном процессе

Qt Quick и Dear ImGui отвергнуты: без серьёзной работы над стилями они выглядят
как отладочные панели, а интерфейс здесь — лицо продукта.

Приложение — **один процесс**:

```
sintence.exe
  ├─ поток: HTTP-сервер на 127.0.0.1, порт выбирается свободный
  └─ главный поток: окно WebView2, внутри собранный Vue
```

Браузера пользователь не видит: ни адресной строки, ни вкладок. WebView2 Runtime
входит в состав Windows 11 (проверено на этой машине: 153.0.4234.32), поэтому
Chromium с собой тащить не надо — этим Electron и отличается в худшую сторону.

Почему HTTP-сервер, а не нативные биндинги WebView2, где JS зовёт C++ напрямую:

- API проверяется `curl`-ом до того, как написана первая строчка Vue;
- фронтенд разрабатывается на статичном JSON, без запущенного C++;
- в C++ качаются сокеты, потоки и роутинг, а не COM-API WebView2;
- окно оверлея, когда до него дойдёт дело, берёт тот же сервер даром.

Цена честно: открытый порт и лишний слой сериализации на каждый запрос. Порт
закрыт от сети (см. ниже), а объёмы здесь такие, что сериализация не видна.

В разработке окно смотрит на `vite dev` (горячая перезагрузка), в релизе — на
собственный сервер, раздающий `web/dist`. Переключение — одна переменная окружения.

## 6. Два ограничения, которые нельзя нарушать

- **Сервер слушает только `127.0.0.1`, никогда `0.0.0.0`.** Иначе статистика
  и управление докачкой уезжают в локальную сеть.
- **Ключ Riot никогда не попадает во фронтенд.** Он живёт в C++ и в переменной
  окружения. Из `POLICY.md`: development-ключ нельзя использовать для поддержки
  публичного продукта, а всё, что ушло в JS, считается опубликованным.

## 7. Оверлей

Реализован тем же стеком: окно с WebView2 и тем же Vue,
`src/app/overlay_window.cpp`. Клавиша PgDn показывает и прячет панель, окно
центрируется на экране и на время показа забирает фокус.

Три ограничения, которые нельзя обойти кодом:

- **Только borderless.** Поверх exclusive fullscreen не отрисуется ни одно
  обычное окно — это ограничение Windows, а не приложения.
- **Перехват клавиши требует низкоуровневого хука.** Игры регистрируют Raw Input
  с флагом `RIDEV_NOHOTKEYS`, который отключает системные горячие клавиши, пока
  игра активна, поэтому `RegisterHotKey` в матче молчит. Хук клавиатуры работает
  в своём процессе и внедрением в игру не является.
- **Прозрачность и клики несовместимы.** Окно было layered с цветовым ключом
  `#FF00FF`, и клики проваливались в игру: hit-test у layered-окна считается
  по видимой области слоя, до `WM_NCHITTEST`. Окно сделано непрозрачным,
  панель занимает его целиком. DirectComposition с попиксельной альфой
  проблему не решает — сквозь альфу мышь проваливается так же.

Подъём окна поверх игры с анти-читом требует прав администратора: манифест
запрашивает их через `/MANIFESTUAC` в `src/CMakeLists.txt`.

Правило границ из §4 оверлей выдержал: ни один заголовок в `core/` ради него
не изменился.

## 8. Профили игроков лобби

По каждому участнику матча приложение показывает, кто это вне игры: тир,
дивизион, LP и W/L соло-очереди плюс три чемпиона с наибольшим мастери —
уровень, очки и дата последней игры на каждом.

Три запроса на игрока, тридцать на лобби:

| Что | Эндпоинт | Хост |
|---|---|---|
| puuid | `account-v1/accounts/by-riot-id` | региональный (`europe`) |
| ранг | `league-v4/entries/by-puuid` | платформенный (`euw1`) |
| мастери | `champion-mastery-v4/…/top?count=3` | платформенный (`euw1`) |

Два разных хоста — главный источник 404 на правильный запрос.

**Лимит ключа связывает, а не лимиты методов.** Personal-ключ даёт
20 запросов в секунду и 100 за 2 минуты на всё вместе; method-лимиты
(2000/10 с у match-v5) при нём недостижимы. Тридцать запросов лобби
укладываются примерно в сорок секунд, поэтому:

- запросы идут через `data/rate_limiter` — скользящие окна, а не
  фиксированные интервалы: Riot считает именно так, и фиксированный
  интервал позволил бы 200 запросов за пару секунд на стыке окон;
- докачка живёт в фоновом потоке `data/profile_service`, а интерфейс
  забирает готовое и показывает прогресс, а не ждёт;
- puuid кешируются: второй матч с тем же человеком не стоит ни одного
  обращения к Riot;
- на 429 читается `Retry-After`, и повтор ровно один.

**Имена чемпионов — забота фронтенда.** Мастери отдаёт только `championId`;
имена лежат в Data Dragon, а это статика на CDN без ключа и без лимитов.
Vue тянет её сам и кеширует в `localStorage` вместе с версией патча —
в `data/` не заводится ещё один справочник, который надо обновлять
на каждом патче.

История матчей (кто на ком играл последние N игр) сюда не входит
намеренно: это по десять запросов на игрока, то есть больше двух минут
на лобби. Она будет по клику на конкретного игрока, а не веером на всех.

## 9. Живой матч: один запрос вместо трёх

`LiveClientSource::LoadGame` ходит только в `/liveclientdata/allgamedata`.
Отдельные `gamestats`, `playerlist` и `activeplayer` относятся к разным
моментам игры, и собранный из них снимок внутренне противоречив; здесь
всё согласовано. Тело 40–80 КБ, но это локальный сокет.

Что оттуда берётся сверх табло:

- **предметы всех десяти** — `allPlayers[].items`, с названием, стаком
  и ценой. Справочник Data Dragon для них не нужен: имена приходят готовыми;
- **уровни Q/W/E/R и пассивки активного игрока** — `activePlayer.abilities`;
- **страница рун активного игрока** — `activePlayer.fullRunes`;
- **золото на руках** — `activePlayer.currentGold`.

Чужие руны и уровни способностей не берутся, потому что Live Client их
не отдаёт. Это ровно та граница, о которой говорит `POLICY.md`: строим на
том, что игрок и так видит, и не достраиваем скрытое состояние.

В режиме наблюдателя и в реплее `activePlayer` приходит строкой с ошибкой
вместо объекта — табло в этом случае возвращается без активного игрока,
а не теряется целиком.

**Регион аккаунта не зашит.** `league-v4` и `champion-mastery-v4` живут на
платформенном хосте, и запрос к чужой платформе отвечает пустым массивом
и 404 — то есть выглядит как «ранга нет», а не как ошибка. Платформа
определяется по puuid запросом `account-v1/region/by-game` и кешируется;
хост из конструктора остаётся только запасным.

## 10. База матчей и пак предпочтений

Приложение показывает активному игроку, как играть в его матчапе: страницу
рун целиком, порядок прокачки и цепочку предметов. Считать это в реальном
времени нельзя — нужны сотни тысяч наблюдений, а ключ даёт 50 запросов
в минуту. Сбор вынесен в отдельный конвейер, и **приложение про базу
не знает вовсе**: оно читает готовый файл.

```
scripts/crawl.py       Riot API -> SQLite (матчи, участники, скиллы, покупки)
scripts/build_pack.py  SQLite   -> project/data/packs/ru-16.19.json + index.json
data/preference_pack   пак      -> хеш-таблица в памяти приложения
app /api/preferences   лобби    -> советы активному игроку по каждому врагу
```

**Советы только для активного игрока, и это не ограничение, а требование.**
Чужие руны и порядок прокачки Live Client не отдаёт никому: показать их
на карточке противника значило бы выдать то, чего игрок видеть не должен
(`POLICY.md`). Про врагов показывается только то, что и так на экране:
предметы, KDA, ранг и пул чемпионов.

**Почему Python.** Часами долбить HTTP и разбирать JSON — работа для ETL,
а не для C++. `sqlite3` и `urllib` есть в стандартной библиотеке, сторонних
зависимостей ноль. Гипотезы «что вообще считать» проверяются в блокноте
над той же базой, и в C++ уезжает только то, что выжило.

**Почему пак, а не SQLite в приложении.** База на сотни мегабайт нужна
исследователю, а продукту нужен ответ. Пак грузится в память целиком:
поиск идёт без диска, без запросов и без ещё одной зависимости в vcpkg.

**Контракт пака задан под будущий сервер.** Приложение сначала читает
`index.json` (патч, имя файла, sha256), потом сам пак. Сегодня это каталог
на диске, завтра — HTTP: меняется одна строка, формат тот же. Тогда же
ключ Riot уедет на сервер и перестанет попадать пользователю — это
и есть единственный настоящий повод завести бэкенд.

### Что знает база

| Таблица | Строк на матч | Откуда |
|---|---|---|
| `matches` | 1 | `match-v5`: патч, очередь, длительность |
| `participants` | 10 | `match-v5`: руны, финальные предметы, итог |
| `skill_order` | 10 | **только** `match-v5/timeline` |
| `purchases` | ~120 | **только** `match-v5/timeline` |

Timeline удваивает цену матча (2 запроса вместо 1) и даёт единственный
источник порядка прокачки и покупок. Проверено на прогоне: ~1430 матчей
в час с timeline против ~2900 без него.

**Ранга участников в `match-v5` больше нет.** Матчу приписывается ранг
того игрока, от которого краулер в него пришёл: соло-очередь рангово
однородна, так что это приличное приближение. В схеме поле называется
`seed_tier`, а не `tier`, — чтобы никто потом не принял оценку за факт.

### Матчапы и лестница отката

Единица агрегата — **чемпион + роль + оппонент по линии + ранговая
корзина**. Оппонента в `match-v5` нет отдельным полем: он выводится из
того, что в матче ровно два игрока с одинаковым `teamPosition` и разными
командами.

Цена этого решения считается заранее и она большая: пар «чемпион+роль»
около 850, а с оппонентом бакетов становится порядка **сорока тысяч**.
При пороге в 30 игр на бакет это ~130 тысяч матчей, то есть девять-десять
ночей сбора, и хвост редких матчапов не наберётся никогда.

Поэтому откат — не аварийный путь, а нормальный режим. Поиск идёт по
лестнице до первого бакета, **в котором есть хоть один вариант**:

```
чемпион | роль | оппонент | корзина игрока   самое точное
чемпион | роль | оппонент | ALL              матчап, любой ранг
чемпион | роль | ANY      | корзина игрока   против всех
чемпион | роль | ANY      | ALL              последнее прибежище
```

Проверка «есть хоть один вариант» обязательна: бакет, где игр набралось,
а повторяющейся сборки нет, бесполезен, и без этой проверки точный матчап
на десяти играх вытеснял бы «против всех» на восьмидесяти.

Что именно нашлось, уезжает во фронт полями `opponent`, `tier` и `exact`,
и интерфейс обязан их показывать: иначе «против всех» прочитается
как «против этого конкретного Ясуо».

### Что показывается

| Блок | Ключ варианта | Почему так |
|---|---|---|
| Руны | вся страница целиком | полстраницы игрок не повторит |
| Прокачка | первые пять повышений | длиннее — варианты перестают повторяться |
| Предметы | первые три законченных, по порядку | это цепочка, а не набор |

«Законченный предмет» определяется по пустому полю `into` в Data Dragon,
а не по цене: Hearthbound Axe стоит 1100 и остаётся полуфабрикатом.

### Две вещи, без которых цифры врут

**Патч.** Сборки устаревают за недели. Агрегат считается по одному патчу,
`crawl.py --prune` выбрасывает остальное. Паки прошлых патчей остаются:
они весят мегабайты и дают запасной вариант на те дни после выхода патча,
когда выборки ещё нет.

**Малая выборка.** Пять побед из пяти — не сигнал. Вариант с выборкой
меньше пяти игр не показывается вовсе, бакет меньше двадцати не попадает
в пак, а сортировка «по силе» идёт по нижней границе интервала Вильсона,
а не по доле побед: она штрафует малые выборки, и вариант с пятью играми
не обгоняет проверенный с пятью сотнями.

Отдельно: долю побед варианта нельзя читать как его пользу. Сборку чаще
доводят до конца в выигранной игре, поэтому у «победных» сборок завышены
и доля, и винрейт. Сравнивать надо с базовым винрейтом чемпиона, который
в паке лежит рядом.
