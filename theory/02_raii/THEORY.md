## RAII

**Resource Acquisition Is Initialization**: время жизни ресурса привязано к времени
жизни объекта. Конструктор захватывает, деструктор освобождает. Больше ничего делать
не нужно — компилятор сам вызовет деструктор на выходе из области видимости,
включая выход по исключению.

```cpp
{
    MatchFile file("match_RU_1.json");   // конструктор: fopen
    // ... работаем ...
}                                        // деструктор: fclose, автоматически
```

Ресурс — это не только память: файловый дескриптор, сокет, мьютекс, соединение с БД.
В Java/C# для этого нужен `finally` или `try-with-resources`, и его легко забыть.
В C++ забыть нельзя: деструктор вызывается всегда.

## Пять специальных функций-членов

```cpp
class MatchPayload {
public:
    ~MatchPayload();                                        // 1. деструктор

    MatchPayload(const MatchPayload& other);                // 2. копирующий конструктор
    MatchPayload& operator=(const MatchPayload& other);     // 3. копирующее присваивание

    MatchPayload(MatchPayload&& other) noexcept;            // 4. перемещающий конструктор
    MatchPayload& operator=(MatchPayload&& other) noexcept; // 5. перемещающее присваивание
};
```

Компилятор генерирует их сам, если ты не написал. Сгенерированные копируют **поля
как есть**: для `std::string` это правильно, для сырого `char*` — копируется указатель,
а не то, на что он указывает. Два объекта, один буфер, два деструктора → двойное
освобождение.

## Правило 0 / 3 / 5

**Правило 0.** Не пиши ни одну из пяти. Работает, когда все поля — типы, которые
управляют собой сами (`std::string`, `std::vector`, `std::unique_ptr`). Это состояние
по умолчанию и цель: сгенерированные функции корректны и бесплатны.

**Правило 3.** Написал одну из тройки (деструктор, копирующий конструктор, копирующее
присваивание) — напиши все три. Раз тебе понадобился деструктор, значит объект чем-то
владеет, значит копирование по умолчанию уже сломано.

**Правило 5.** То же плюс перемещение — иначе тип будет копироваться там, где мог бы
перемещаться.

**Явное лучше неявного:**

```cpp
MatchFile(const MatchFile&) = delete;             // копировать нельзя, и это видно
MatchFile& operator=(const MatchFile&) = delete;
MatchPayload(MatchPayload&&) noexcept = default;  // сгенерируй, но покажи, что я подумал
```

`= delete` — не отсутствие функции, а функция, вызов которой это ошибка компиляции.
Сообщение получится внятное, вместо тихой поломки в рантайме.

## Перемещение

```cpp
MatchPayload a(text);
MatchPayload b(std::move(a));   // b забрал буфер, a остался пустым
```

- **`std::move` ничего не перемещает.** Это приведение типа к `T&&` — «этот объект
  больше не нужен, можешь забрать его внутренности». Работу делает конструктор.
- **Перемещённый объект остаётся валидным, но с неопределённым содержимым.** Его можно
  разрушить и присвоить ему заново; нельзя рассчитывать на то, что в нём лежит.
  Для *своего* типа контракт задаёшь ты сам — и тогда его можно проверить тестом.
- **`noexcept` на перемещении обязателен.** `std::vector` при расширении выбирает:
  перемещать или копировать. Если твой move может бросить исключение, вектор
  не рискнёт и будет копировать — молча, без единого сообщения.
- **Параметр по значению + `std::move` в поле** — то, что ты уже писал в теме 1:
  вызывающий сам решает, отдать копию или временный объект.

## Как это пишется на C++23

**Тело перемещающего конструктора — это `std::exchange`.** Забрать чужое поле и оставить
источнику валидное пустое значение, одной строкой, без шанса забыть второй шаг:

```cpp
MatchPayload::MatchPayload(MatchPayload&& other) noexcept
    : data_(std::exchange(other.data_, nullptr)),
      size_(std::exchange(other.size_, 0)) {
}
```

Классическая ошибка «забрал указатель, но не занулил чужой» здесь физически не пишется:
`exchange` возвращает старое значение и кладёт новое за один вызов.

**Владение — `std::unique_ptr`, а не сырой указатель.** Правило 0 работает ровно потому,
что поле умеет освобождать себя само:

```cpp
std::unique_ptr<MatchPayload> payload = std::make_unique<MatchPayload>(text);
```

`unique_ptr` некопируемый и перемещаемый — то есть твой класс с таким полем получает
корректные сгенерированные пять функций бесплатно. Задачи 2.1 и 2.2 требуют написать
всё руками один раз, чтобы стало видно, что именно он делает за тебя.

**Конструктор не умеет вернуть ошибку.** Либо бросает исключение, либо объект создаёт
фабричная функция, возвращающая `std::expected<MatchFile, OpenError>` (C++23). Что выбрать
и почему — тема 7; сейчас достаточно знать, что «конструктор молча оставил объект
в нерабочем состоянии» — это не третий вариант, а баг.

## Пять ошибок этой темы

| Что сделал | Что увидишь |
|---|---|
| скопировал объект с сырым указателем | ничего при компиляции; ASan: `attempting double-free` или `heap-use-after-free` при выходе из области видимости |
| написал копирующее присваивание без проверки самоприсваивания | ASan: `heap-use-after-free` на `a = a` — освободил буфер и тут же читаешь из него |
| объявил перемещающий конструктор, забыл про копирование | `C2280: попытка ссылки на удалённую функцию` / `error: use of deleted function` — объявленный move **убирает** сгенерированную копию |
| забыл `std::move` при передаче в поле | ничего: ни ошибки, ни предупреждения, просто лишняя копия. Самая дорогая ошибка темы |
| `std::move` от `const`-объекта | тоже ничего: `const T&&` не подходит к `T&&`, тихо вызывается копирование |

Первые две ловятся только санитайзером — поэтому Debug и собирается с ASan с первого дня.
Компилятор здесь молчит: он не знает, что твой `char*` кому-то принадлежит.

## Читать в книгах

- **«Чистый код», глава 10 «Классы».** Раздел про единственную ответственность: класс,
  который владеет ресурсом, тем и занимается — открывает, отдаёт, закрывает. Как только
  он начинает ещё и парсить содержимое, деструктор перестаёт быть очевидным.
  У Мартина примеры на Java, где деструкторов нет вовсе и освобождение живёт
  в `finally` у вызывающего кода; в C++ ответственность переносится внутрь класса,
  и потому её видно в одном месте, а не в каждом месте использования.

один раз написать всё руками именно затем, чтобы стало понятно, что именно
`std::vector` и `std::unique_ptr` делают за тебя.
