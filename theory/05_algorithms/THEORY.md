## 1. Зачем эта тема нужна

Посмотри на свою `MostPlayedChampion` из задачи 4.1: восемь строк цикла, две переменные
состояния (`best_count`, `champion_name`), ручное сравнение. Функция делает одну
стандартную вещь — «найди максимум по критерию», — но написана так, что читающий
обязан прочитать весь цикл, чтобы это понять.

Алгоритмы STL — это набор уже написанных циклов с именами. `max_element` вместо цикла
с бегущим максимумом, `count_if` вместо цикла со счётчиком, `sort` вместо любой
сортировки, которую ты написал бы руками. Выигрыш не в скорости (цикл руками не
медленнее) — выигрыш в том, что **имя алгоритма говорит о намерении**, а цикл требует
чтения тела. «Чистый код» называет это одним уровнем абстракции на функцию.

Вторая половина темы — **лямбды**: способ передать алгоритму «по какому именно критерию».
Без них алгоритмы годятся только на «отсортируй по возрастанию», а тебе нужно
«по числу игр, по убыванию, при равенстве — по алфавиту».

**Где это в анализаторе.** Топ чемпионов по играм, по winrate, по KDA; фильтры
«только мид», «только где игр больше 30»; агрегаты «сколько всего игр». Всё, что
в интерфейсе будет колонкой с сортировкой по клику, здесь и появляется.

## 2. Лямбды

### Что это

Лямбда — это **объект с оператором вызова**, который компилятор генерирует за тебя.
Не указатель на функцию, не макрос: настоящий объект, у него есть тип (безымянный),
его можно хранить в переменной, копировать и передавать.

```cpp
auto is_positive = [](int n) { return n > 0; };   // объявили
bool yes = is_positive(5);                        // вызвали: true
```

Читается так: `[]` — список захвата (см. ниже), `(int n)` — параметры как у обычной
функции, `{ ... }` — тело. Тип возвращаемого значения компилятор выводит сам.

Зачем это нужно, если есть обычные функции: лямбду можно объявить **прямо в точке
использования**, там, где она нужна, и она видит локальные переменные вокруг себя.
Отдельная функция ни того, ни другого не умеет.

### Захват: `[]`, `[x]`, `[&x]`

Тело лямбды не видит локальные переменные автоматически — их нужно **захватить**,
перечислив в квадратных скобках. Это главное, что отличает лямбду от функции.

```cpp
int min_games = 30;

auto by_value     = [min_games](int games) { return games >= min_games; };  // копия
auto by_reference = [&min_games](int games) { return games >= min_games; }; // ссылка
auto nothing      = [](int games) { return games >= min_games; };  // ОШИБКА компиляции
```

Последняя строка не соберётся: `error C3493: min_games не может быть захвачено неявно`
/ `'min_games' is not captured`. Компилятор прямо говорит, чего не хватает.

| Захват | Что значит | Когда брать |
|---|---|---|
| `[x]` | копия `x` в момент создания лямбды | дёшево копируется (`int`, `bool`, `double`) |
| `[&x]` | ссылка на `x` | дорого копировать, либо лямбда должна видеть изменения |
| `[=]` | копии всего, что используется | не использовать: непонятно, что реально захвачено |
| `[&]` | ссылки на всё, что используется | не использовать по той же причине |
| `[this]` | указатель на объект, `поля_` видны напрямую | внутри метода класса |

Правило для этого курса: **захватывай поимённо**. `[=]` и `[&]` выглядят удобно ровно
до первого раза, когда лямбда пережила то, на что ссылалась.

### Главная опасность: висячий захват

Захват по ссылке живёт ровно столько, сколько живёт оригинал:

```cpp
std::function<bool(int)> MakeFilter() {
    int min_games = 30;
    return [&min_games](int g) { return g >= min_games; };   // ССЫЛКА НА МЁРТВОЕ
}                                                            // min_games умер здесь
```

Компилятор молчит, вызов «работает», читая мусор со стека. ASan скажет
`stack-use-after-return`. Если лямбда переживает область видимости — захват только
по значению.

Пока лямбда используется *на месте* (передана в `std::sort` и там же отработала) —
`[&]` безопасен, потому что алгоритм отработает до выхода из функции.

### `mutable` и возвращаемый тип

```cpp
auto counter = [count = 0]() mutable { return ++count; };   // mutable: можно менять копию
auto ratio = [](int a, int b) -> double { return a / (double)b; };   // тип возврата явно
```

`mutable` нужен редко; явный `-> тип` — когда вывод даёт не то, что ты хотел
(классика: вернул `int` там, где ждал `double`).

### Обобщённая лямбда

```cpp
auto by_second = [](const auto& a, const auto& b) { return a.second > b.second; };
```

`auto` в параметрах — лямбда работает с любым типом, у которого есть `.second`.
Для компараторов к контейнерам пар это избавляет от выписывания
`const std::pair<const std::string, int>&` целиком (и от ошибки с забытым `const`
у ключа, которую иначе получишь).

## 3. Алгоритмы: общая форма

Все алгоритмы живут в `<algorithm>` (плюс `<numeric>` для арифметики) и бывают в двух
видах — старый и современный:

```cpp
std::sort(v.begin(), v.end());        // классический: пара итераторов
std::ranges::sort(v);                 // ranges (C++20): диапазон целиком
```

**В этом курсе пишем `std::ranges::` версию.** Причины ровно две, обе практические:
нельзя случайно передать `begin()` от одного контейнера и `end()` от другого
(частая ошибка, компилятор её не ловит), и есть проекции — см. раздел 7.

Общая форма у почти всех одинакова:

```cpp
std::ranges::алгоритм(диапазон, предикат_или_компаратор, проекция);
```

Где **предикат** — функция, возвращающая `bool` («подходит ли элемент»),
а **компаратор** — функция от двух элементов, возвращающая «первый должен идти раньше».

## 4. Сортировка

### `sort` с компаратором

```cpp
std::vector<ChampionGames> rows = ...;

std::ranges::sort(rows, [](const ChampionGames& a, const ChampionGames& b) {
    return a.games > b.games;          // по убыванию числа игр
});
```

Компаратор отвечает на один вопрос: **«должен ли `a` стоять строго раньше `b`»**.
Не «равны ли», не «больше или равно» — строго раньше. Отсюда главное правило:

> **`<=` и `>=` в компараторе — ошибка.** Только `<` и `>`.

Причина: алгоритму нужно, чтобы `comp(a, a)` было `false` (элемент не может идти
раньше самого себя). С `<=` это `true`, и `std::sort` выходит за границы массива.
На твоей сборке (Debug + отладочная STL) программа не сортирует, а **падает**:
abort, код возврата 3, сообщение про `invalid comparator`. В Release — тихая порча
памяти. Проверено на этой машине специально, чтобы ты знал, как это выглядит.

### Ничьи и стабильность

`sort` **не стабилен**: элементы с одинаковым ключом могут поменяться местами
непредсказуемо. Два способа получить определённый порядок:

```cpp
// 1. Тай-брейк прямо в компараторе — предпочтительно, порядок задан явно
std::ranges::sort(rows, [](const auto& a, const auto& b) {
    if (a.games != b.games) return a.games > b.games;   // основной ключ
    return a.champion_name < b.champion_name;           // при равенстве — по имени
});

// 2. stable_sort — сохраняет исходный порядок равных элементов
std::ranges::stable_sort(rows, {}, &ChampionGames::games);
```

Первый способ лучше тем, что контракт («при равенстве — по алфавиту») записан в коде
и проверяется тестом, а не зависит от того, в каком порядке данные пришли.

Это ровно та проблема, которую ты в задаче 4.1 обошёл случайно: там порядок дал
`std::map` (ключи отсортированы), а строгое `>` не перезаписывало уже найденный
максимум. Здесь данные приходят вектором, и порядок приходится задавать самому.

### Топ-N без полной сортировки

Если нужны только первые 5 из 200, сортировать все 200 незачем:

```cpp
std::ranges::partial_sort(rows, rows.begin() + 5, comp);   // первые 5 на местах
```

`O(n log k)` вместо `O(n log n)`. На 50 чемпионах разница незаметна, на списке матчей
в теме 12 — заметна. Знать, что такой инструмент есть, важнее, чем применять его сейчас.

## 5. Алгоритмы-вопросы

Эти ничего не меняют, только отвечают:

```cpp
// сколько элементов подходят
const auto n = std::ranges::count_if(reports, [](const ChampionReport& r) {
    return r.HasEnoughData();
});

// есть ли хотя бы один
const bool any = std::ranges::any_of(reports, [](const ChampionReport& r) {
    return r.Winrate() > 0.6;
});

// все ли / ни один ли
std::ranges::all_of(reports, pred);
std::ranges::none_of(reports, pred);

// первый подходящий: итератор или end()
const auto it = std::ranges::find_if(reports, pred);
if (it != reports.end()) { /* ... */ }

// максимум/минимум по критерию: итератор, а не значение
const auto best = std::ranges::max_element(reports, {}, &ChampionReport::Games);
```

`count_if` возвращает знаковый тип (`std::ptrdiff_t`), а не `int` — при возврате из
функции, объявленной как `int`, нужен `static_cast<int>`, иначе получишь `C4267`/`C4244`.
Ту же самую warning ты уже видел в `champion_report.cpp:31`.

`max_element` на **пустом** диапазоне возвращает `end()` — разыменовывать нельзя.
Проверка на пустоту остаётся твоей работой.

## 6. Алгоритмы-преобразования

```cpp
// отобрать подходящие в новый вектор
std::vector<std::string> names;
std::ranges::copy_if(all_names, std::back_inserter(names), pred);

// превратить каждый элемент в другой
std::ranges::transform(reports, std::back_inserter(names), &ChampionReport::ChampionName);

// свернуть диапазон в одно значение (C++23)
const int total = std::ranges::fold_left(reports, 0, [](int acc, const ChampionReport& r) {
    return acc + r.Games();
});
```

`fold_left` — это C++23-замена `std::accumulate` из `<numeric>`: то же самое
(начальное значение плюс функция «накопитель + элемент → новый накопитель»),
но работает с диапазоном целиком и не притворяется, что умеет только складывать.
`accumulate` тоже никуда не делся — увидишь его в любом коде до 2023 года.

`std::back_inserter` — адаптер, который превращает «записать в итератор» в
`push_back`. Без него алгоритм писал бы в уже существующие элементы, а их нет.
В следующем разделе он не понадобится вовсе.

## 7. Проекции

Проекция — третий аргумент почти любого `ranges`-алгоритма: «к чему применять
критерий». Она убирает половину лямбд, которые иначе пришлось бы писать:

```cpp
// без проекции
std::ranges::sort(rows, [](const auto& a, const auto& b) {
    return a.games < b.games;
});

// с проекцией: «сортируй как обычно (<), но смотри на поле games»
std::ranges::sort(rows, {}, &ChampionGames::games);

// по убыванию
std::ranges::sort(rows, std::ranges::greater{}, &ChampionGames::games);
```

`{}` на месте компаратора означает «по умолчанию», то есть `std::ranges::less`.
`&ChampionGames::games` — указатель на член: не вызов, а «вот это поле». Работает
и с методами: `&ChampionReport::Games` возьмёт результат вызова метода.

Читается вслух буквально: «отсортируй `rows` по убыванию по полю `games`».
Лямбда из трёх строк схлопнулась в два слова — и в ней больше нечему ломаться.

**Важно, и на этом спотыкаются все, включая меня при написании этой карточки:
проекция применяется ДО предиката.** Если проекция задана, лямбда получает уже
спроецированное значение, а не исходный элемент:

```cpp
// предикат получает пару целиком — проекции нет
std::ranges::count_if(games, [](const auto& kv) { return kv.second >= 9; });

// предикат получает int — проекция уже достала .second
std::ranges::count_if(games, [](int count) { return count >= 9; },
                      &std::pair<const std::string, int>::second);

// а так не соберётся: проекция даёт int, а лямбда ждёт пару
std::ranges::count_if(games, [](const auto& kv) { return kv.second >= 9; },
                      &std::pair<const std::string, int>::second);
```

Ошибка выглядит страшно — простыня из `concepts(248): концепт "std::invocable<...>"
вычислен как false`. Читается она с конца: «предикат нельзя вызвать с тем типом,
который даёт проекция». Это стандартный вид ошибки в ranges: ищи слово `invocable`
и смотри, какой тип в него подставлен.

## 8. `views`: ленивые конвейеры

`views` — способ описать цепочку «отфильтровать → преобразовать → взять первые N»
без создания промежуточных векторов:

```cpp
auto top_names = reports
    | std::views::filter([](const ChampionReport& r) { return r.HasEnoughData(); })
    | std::views::transform(&ChampionReport::ChampionName)
    | std::views::take(5)
    | std::ranges::to<std::vector>();          // C++23: материализовать в вектор
```

Ключевое слово — **ленивые**. `views::filter(...)` ничего не фильтрует в момент
написания: он строит описание. Реальная работа происходит, только когда по результату
кто-то идёт — в цикле `for` или в `ranges::to`. Поэтому цепочка из трёх `views`
проходит по данным **один раз**, а не три.

`std::ranges::to<std::vector>()` (C++23) — конец конвейера: «сделай из этого
настоящий вектор». До C++23 для этого писали цикл с `push_back`.

**Ловушка ленивости:** view не владеет данными, он на них ссылается. View,
переживший свой контейнер, — то же самое, что висячая ссылка:

```cpp
auto BadView() {
    std::vector<int> local{1, 2, 3};
    return local | std::views::filter(pred);   // local умрёт, view останется
}
```

Правило: **view — временный объект внутри одной функции.** Возвращать наружу
следует материализованный `std::vector` через `ranges::to`.

## 9. Разбор: `MostPlayedChampion` в одну строку

Твой код из задачи 4.1:

```cpp
std::string MostPlayedChampion(const std::map<std::string, int>& games) {
    if (games.empty()) {
        return "";
    }
    int best_count = 0;
    std::string champion_name;
    for (const auto& [name, count] : games) {
        if (count > best_count) {
            best_count = count;
            champion_name = name;
        }
    }
    return champion_name;
}
```

Через алгоритм это:

```cpp
std::string MostPlayedChampion(const std::map<std::string, int>& games) {
    if (games.empty()) {
        return "";
    }
    const auto best = std::ranges::max_element(games, {}, &std::pair<const std::string, int>::second);
    return best->first;
}
```

Что здесь произошло по шагам:

- `max_element` — тот самый цикл с бегущим максимумом, уже написанный и отлаженный;
- проекция `&pair::second` говорит «сравнивай по значению, не по ключу»;
- вернулся **итератор**, поэтому `best->first` — имя;
- проверка на пустоту осталась: на пустом диапазоне `max_element` даёт `end()`.

Чего этот вариант **не** делает сам — тай-брейк. `max_element` возвращает **первый**
максимальный элемент, а `std::map` обходится по возрастанию ключа, поэтому
лексикографически меньший и окажется первым. Тот же аргумент, что и в 4.1: работает
не случайно, но держится на свойстве `map`. Для вектора, где порядок произвольный,
пришлось бы писать компаратор с тай-брейком явно.

Переписывать 4.1 не нужно — это разбор, а не задание. Но сравни две версии: вторая
короче не ради краткости, а потому что «найти максимум по критерию» в ней написано
один раз словом, а не восемью строками, которые ещё надо прочитать.

## 10. Шесть ошибок этой темы

| Что сделал | Что увидишь |
|---|---|
| `<=` или `>=` в компараторе | Debug: падение с `abort`, код 3, `invalid comparator`; Release — тихая порча памяти |
| `std::ranges::sort(m)` для `std::map` / `std::set` | `error C2672` / `no matching function`: сортировка требует random-access итераторов, а у дерева их нет. Копируй в `vector` и сортируй его |
| забыл захватить переменную в лямбде | `C3493: не может быть захвачено, так как не имеет спецификатора захвата по умолчанию` / `not captured` |
| захватил по ссылке то, что умрёт раньше лямбды | ничего при компиляции; ASan: `stack-use-after-return` |
| разыменовал `end()` от `find_if` / `max_element` на пустом диапазоне | ASan: `heap-buffer-overflow`, либо мусор в результате |
| вернул `view` из функции | ничего при компиляции; ASan: `heap-use-after-free` при чтении. Материализуй через `ranges::to` |

Первая и последние две — только санитайзер. Вторая и третья — компилятор, сразу.

## 11. Читать в книгах

- **«Грокаем алгоритмы», глава 1 (бинарный поиск)** и **глава 4 (быстрая сортировка).**
  Четвёртая — прямо про то, что внутри `std::sort`: разделяй и властвуй, `O(n log n)`
  в среднем. Стоит прочитать до того, как начнёшь сортировать вслепую: понимание,
  почему сортировка стоит `n log n`, а не `n`, объясняет, зачем существует
  `partial_sort`.
- **«Грокаем алгоритмы», глава 2 (массивы и связанные списки).** Почему `sort`
  требует массив с произвольным доступом и не работает на дереве `map`.
- **«Грокаем алгоритмы», глава 10 (k ближайших соседей)** — по диагонали: там
  впервые появляется «отсортировать по вычисленному признаку», то есть ровно
  проекция, только руками.
- **«Чистый код», глава 3 «Функции».** Один уровень абстракции на функцию —
  главный аргумент в пользу алгоритмов вместо циклов: `count_if(reports, pred)`
  и цикл с `++n` находятся на разных уровнях, и смешивать их в одной функции
  значит заставлять читателя переключаться.

> Сверь номера глав со своим изданием при первом обращении — в русских переводах
> нумерация иногда съезжает.

## 12. ВЫПИСАТЬ В БЛОКНОТ

```
ЛЯМБДА
  [захват](параметры) { тело }
  [x]      копия            [&x]   ссылка (только если лямбда не переживёт x)
  [=] [&]  не использовать: непонятно, что захвачено
  -> тип   когда вывод даёт не то (int вместо double)

АЛГОРИТМЫ (пишем ranges-версии, #include <algorithm>)
  ranges::sort(v, comp, proj)          отсортировать
  ranges::stable_sort(v, comp, proj)   то же, равные не переставляются
  ranges::partial_sort(v, v.begin()+n) только первые n на местах
  ranges::count_if(v, pred)            сколько подходит (ptrdiff_t!)
  ranges::any_of / all_of / none_of    есть ли / все ли / ни одного
  ranges::find_if(v, pred)             первый подходящий -> итератор или end()
  ranges::max_element(v, {}, proj)     максимум -> ИТЕРАТОР (end() на пустом!)
  ranges::fold_left(v, init, f)        свернуть в одно значение (C++23)

ПРОЕКЦИЯ — третий аргумент, «к чему применять критерий»
  ranges::sort(rows, {}, &Row::games)                  по возрастанию поля
  ranges::sort(rows, ranges::greater{}, &Row::games)   по убыванию поля
  {} на месте компаратора = «по умолчанию» (less)

КОМПАРАТОР
  отвечает «должен ли a идти СТРОГО раньше b»
  только < и >, никогда <= и >=      (иначе abort, код 3)
  sort не стабилен: ничью задавай явно вторым ключом в компараторе

VIEWS (ленивые, #include <ranges>)
  v | views::filter(pred) | views::transform(proj) | views::take(n)
  | ranges::to<std::vector>()      материализовать (C++23)
  view НЕ владеет данными: не возвращать наружу, не переживать контейнер

ЧЕГО НЕЛЬЗЯ
  sort по std::map / std::set        нет random-access итераторов
  разыменовать end()                 проверяй пустоту до max_element/find_if
```
