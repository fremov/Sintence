# Тема 0. Единицы трансляции, заголовки, компилятор против линкера

Справочная карточка. Читается за минуту перед задачей и грепается через полгода.
Глубина — в Практикуме и книгах.

## Конвейер

```
main.cpp ─┐
          ├─→ препроцессор → компилятор → main.obj ─┐
kda.h   ──┘                                         ├─→ линкер → analyzer.exe
                                                    │
kda.cpp ──→ препроцессор → компилятор → kda.obj ────┘
```

- **Препроцессор** тупо подставляет текст: `#include` — это буквально «вставь сюда файл целиком».
- **Компилятор** видит ровно одну единицу трансляции (`.cpp` + всё, что он втянул) и ничего не знает про остальные файлы. Проверяет синтаксис и типы, порождает объектный файл.
- **Линкер** складывает все объектные файлы и связывает вызовы с телами функций по именам символов. Про типы и синтаксис он уже ничего не знает — только про имена.

Отсюда главное правило чтения ошибок: **кто ругается, тот и подсказывает, где искать.**
Ошибка компилятора — проблема внутри одного файла. Ошибка линкера — проблема между файлами.

## Что где лежит

| В заголовке (`.h`) | В реализации (`.cpp`) |
|---|---|
| объявления функций `double ComputeKda(const Kda&);` | определения функций (тела) |
| определения типов `struct Kda { ... };` | внутренние функции файла |
| `inline`-функции и `constexpr`-константы | всё остальное |
| шаблоны (целиком, вместе с телом) | |

**Объявление** — обещание, что символ существует. **Определение** — сам символ.
Объявлений может быть сколько угодно, определение одно. Это и есть ODR — One Definition Rule.

## Идиомы

```cpp
#ifndef COURSE_KDA_H          // include guard: защита от повторного
#define COURSE_KDA_H          // включения в одну единицу трансляции
// ...
#endif  // COURSE_KDA_H

#pragma once                  // то же самое одной строкой, поддерживают все
                              // актуальные компиляторы

inline bool IsPerfect(int d)  // inline разрешает одинаковые определения
{ return d == 0; }            // в разных единицах трансляции

#include "kda.h"              // кавычки — свой файл, поиск рядом
#include <vector>             // угловые скобки — системный/сторонний
```

Порядок `#include` в `.cpp`: сначала свой заголовок, потом стандартная библиотека, потом чужие.
Свой первым — чтобы он сломался сам, если забыл в нём что-то включить.

## Модули: почему их здесь нет

Курс собирается с `-std=c++23` / `/std:c++latest`, и на этой машине уже работает
`import std;` — вся стандартная библиотека одним объявлением, без препроцессора
и без повторного разбора заголовков в каждой единице трансляции. Проверено:
`cl /std:c++latest /c "%VCToolsInstallDir%modules\std.ixx"` плюс `import std;` в файле
собирается и печатает.

Курс всё равно остаётся на `#include` до темы 11, и причин две. Первая: doctest —
обычный заголовок, и весь мир библиотек вокруг тоже; смешивать модули и заголовки
можно, но диагностика при этом становится хуже, а не лучше. Вторая и главная: модули
прячут ровно тот механизм, который ты сейчас изучаешь. `LNK2019` разбирается один раз
в жизни, и лучше на голом конвейере «препроцессор → компилятор → линкер».

Знать сейчас достаточно: единица трансляции, ODR и линкер никуда не делись —
модуль меняет способ доставки объявлений, а не то, как собирается программа.

## Пять ошибок этой темы

| Что сделал | Что увидишь | Кто ругается |
|---|---|---|
| объявил функцию, не написал тело | `LNK2019: неразрешённый внешний символ` / `undefined reference to` | линкер |
| в определении другой тип параметра, чем в объявлении | **та же** `LNK2019` | линкер |
| забыл include guard, заголовок включился дважды | `C2011: переопределение типа "struct"` / `redefinition of 'struct'` | компилятор |
| положил тело функции в заголовок, включил его в два `.cpp` | `LNK2005: уже определён в main.obj` / `multiple definition of` | линкер |
| забыл `#include` для типа, который используешь | `C2065: необъявленный идентификатор` / `'X' was not declared in this scope` | компилятор |

Первые две строки — самое важное в теме. **Одна ошибка, две разные причины.**
Отличаются только именем символа внутри сообщения: MSVC печатает декорированное
`?ComputeKda@@YANHHH@Z`, GCC — читаемое `ComputeKda(int, int, int)`. Сравни его с тем,
что реально написано в `.cpp` — расхождение станет видно сразу.

## Как читать ошибку

1. **Первая строка, а не последняя.** Всё, что после первой ошибки компилятора, — как правило, её последствия.
2. **Номер строки часто врёт.** Компилятор указывает, где он споткнулся, а не где ты ошибся: пропущенная `;` в конце класса всплывёт на десять строк ниже.
3. **`LNK` в начале кода — это линкер.** Файл, в котором «не нашлось», в тексте есть: `main.obj : error LNK2019 ... в функции main`.

## Практика

их надо собирать руками; команды и ожидаемые сообщения — в `experiments/README.md`.

трансляции, всё собирается и проходит `ctest`. Читай комментарии в нём, чинить там нечего.

## Читать в книгах

- **«Чистый код», глава 5 «Форматирование».** Смотри раздел про вертикальное форматирование и «газетную метафору»: файл читается сверху вниз, общее выше частного. Ровно так устроен заголовок — сначала типы и объявления, которые нужны читателю, детали ниже. Примеры Мартина на Java, где заголовков нет вовсе; в C++ разделение «интерфейс/реализация» физическое, на уровне файлов, и потому дисциплинирует сильнее.

## Где это в анализаторе

Каждый следующий тип — `Champion`, `PlayerStats`, `MatchLine`, парсер JSON, HTTP-клиент —
это пара «заголовок + реализация». К теме 11 их будет три десятка, и граница между
«что видно снаружи» и «что внутри» станет главным архитектурным инструментом. Тема 0 —
это тот момент, когда `undefined reference` перестаёт быть загадкой и становится опечаткой,
которую видно за десять секунд.
