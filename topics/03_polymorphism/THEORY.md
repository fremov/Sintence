## Зачем эта тема вообще нужна

У анализатора будет три реально разных источника матчей: HTTP-запрос к Match-V5
(тема 15), локальный сервер `127.0.0.1:2999` во время матча (Live Client Data),
файлы фикстур для тестов — и ни один не похож на другой ни по коду, ни по скорости,
ни по надёжности. Без этой темы код анализа обзавёлся бы веткой `if (source_type == …)`
на каждый из них, и с четвёртым источником (LCU) их стало бы четыре, а с пятым — пять.

Полиморфизм — способ вообще не писать эту ветку. Анализатор работает с одним
понятием «источник матчей», и не важно, реализовано оно диском, сетью или списком
в памяти для теста. Тема 2 (RAII) отвечала за то, кто владеет ресурсом; эта тема —
за то, как разные вещи предъявляют одинаковое поведение наружу.

**Где именно в анализаторе:** `project/ARCHITECTURE.md`, пункт 1. Три источника
данных (Match-V5, Live Client Data, LCU) плюс фикстуры реализуют один интерфейс
`MatchSource`; слой `analysis/` работает только с ним и не знает, кто именно
ему достался. Задача 3.3 — первая функция этого слоя, и её проверка на то, что
тема усвоена: `BuildChampionIndex` не содержит ни одного `if` про тип источника.

## Интерфейс в C++

Зачем: `MatchSource` объявляет только *что* умеет источник, ни слова о *как*.
Это тот самый контракт, с которым дальше работает весь остальной код, не зная,
файл перед ним, сеть или список в памяти.

Отдельного ключевого слова `interface` нет. Интерфейс — это класс, у которого все
методы чисто виртуальные, а деструктор виртуальный:

```cpp
class MatchSource {
public:
    virtual ~MatchSource() = default;                        // обязательно виртуальный

    virtual std::string Name() const = 0;                    // = 0 — чисто виртуальный
    virtual bool IsAvailable() const = 0;
    virtual std::vector<MatchEntry> LoadMatches() const = 0;
};
```

`= 0` означает «тела нет, реализовать обязан наследник». Класс с хотя бы одним таким
методом — **абстрактный**: создать его объект нельзя, можно только унаследоваться.

## Наследование и переопределение

Зачем: `FixtureMatchSource` обещает выполнить контракт `MatchSource`. `override`
делает это обещание проверяемым компилятором, а не честным словом.

```cpp
class FixtureMatchSource : public MatchSource {
public:
    std::string Name() const override;                       // override — не для красоты
    bool IsAvailable() const override;
    std::vector<MatchEntry> LoadMatches() const override;
};
```

`public` перед именем базы обязателен: без него наследование приватное, и
`FixtureMatchSource` перестанет быть `MatchSource` для внешнего кода.

**`override` ставится всегда.** Он не меняет поведение — он заставляет компилятор
проверить, что метод действительно переопределяет виртуальный метод базы. Без него
опечатка в сигнатуре (потерянный `const`, `std::string` вместо `const std::string&`)
создаёт новый метод, который никто никогда не вызовет, и программа тихо работает
неправильно.

## Динамический полиморфизм

Зачем: это и есть механизм, который убирает `if (source_type == …)` из кода
анализа. `BuildChampionIndex` (задача 3.3) вызывает `source.LoadMatches()`
один раз, а какая реализация реально отработает — решает не он.

Вызов виртуального метода выбирает реализацию по **фактическому** типу объекта,
а не по типу указателя или ссылки:

```cpp
void PrintSourceName(const MatchSource& source) {
    std::cout << source.Name();          // какая именно — решится в рантайме
}

FixtureMatchSource fixtures(...);
PrintSourceName(fixtures);               // напечатает "fixtures"
```

Работает **только через ссылку или указатель на базу**. По значению — не работает:
объект копируется в базовую часть, производная отрезается (**срезка**, object slicing),
и виртуальность теряется. Для абстрактной базы это даже не скомпилируется, что и хорошо.

## Правило пяти для интерфейса

Зачем: `MatchSource` хранится в `FallbackMatchSource` как указатель на базу
(задача 3.2). Если бы интерфейс копировался, копия через базовый указатель
срезала бы производную часть — баг, который не покажет ни один тест на
пустых данных, только на реальных двух разных источниках.

Виртуальный деструктор — это объявленная спецфункция, значит правило 3/5 из темы 2
включается: сгенерированные копирование и перемещение исчезают или становятся опасными.
Для интерфейса идиома такая:

```cpp
class MatchSource {
public:
    virtual ~MatchSource() = default;
    MatchSource(const MatchSource&) = delete;                // копировать интерфейс незачем
    MatchSource& operator=(const MatchSource&) = delete;
protected:
    MatchSource() = default;                                 // создавать — только наследникам
};
```

Копирование запрещено не из вредности: копия через базовую ссылку скопировала бы
только базовую часть — ровно та срезка, о которой выше.

## Пять ошибок этой темы

| Что сделал | Что увидишь |
|---|---|
| забыл `virtual` у деструктора базы | ничего при компиляции; `delete` через указатель на базу не вызовет деструктор наследника → ASan: `detected memory leaks` |
| забыл `override`, разошлась сигнатура (обычно потерян `const`) | ничего: метод базы остался чисто виртуальным → `C2259: невозможно создать экземпляр абстрактного класса` / `error: cannot declare variable to be of abstract type` |
| написал `override`, а сигнатура не совпала | `C3668: метод с описателем override не переопределяет ни одного метода базового класса` — то самое сообщение, ради которого `override` и пишут |
| забыл `public` при наследовании | `C2243 / error: cannot cast ... to inaccessible base` при попытке передать наследника как базу |
| передал наследника в функцию **по значению** через базовый тип | `C2259` для абстрактной базы; для неабстрактной — компилируется и молча теряет поведение наследника |

Первая ловится только санитайзером, третья и четвёртая — компилятором сразу.
Именно поэтому `override` пишется на каждом переопределении без исключений.

## Читать в книгах

- **«Чистый код», глава 6 «Объекты и структуры данных».** Разница между объектом
  (скрывает данные, выставляет поведение) и структурой (выставляет данные, поведения
  нет). `MatchSource` — объект в чистом виде: снаружи видно только «дай матчи»,
  а откуда они берутся — из файла, из сети или из клиента игры — не видно вообще.
  `MatchEntry` — структура: голые поля, никаких инвариантов.
- **«Чистый код», глава 11 «Системы».** Про отделение конструирования от использования:
  кто именно создаёт конкретный источник — решается в одном месте (тема 11 назовёт его
  `app/`), а весь остальной код принимает уже готовый `const MatchSource&` и никогда
  не знает, что ему передали.
