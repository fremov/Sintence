# Тема 4. Контейнеры STL

## Зачем эта тема нужна

В задаче 3.3 ты написал поиск «есть ли уже отчёт по этому чемпиону» линейным перебором:
на каждую запись — проход по всем уже накопленным отчётам. Ты сам назвал проблему, когда
отвечал на вопрос про 100 000 записей: это `записи × чемпионы` сравнений. На 100 000 записей
и 50 чемпионов — до пяти миллионов сравнений строк там, где нужно было пятьдесят тысяч.

Контейнеры STL — это готовые структуры данных, в которых поиск, вставка и хранение уже
написаны, отлажены и имеют известную стоимость. Вся эта тема — про один вопрос:
**какую структуру выбрать, чтобы операция, которую ты делаешь чаще всего, была дешёвой.**

**Где это в анализаторе.** Пункт «индекс матчей по чемпионам» из `project/ARCHITECTURE.md`:
после этой темы `analysis/` перестаёт быть наивным. Список чемпионов, пул ролей, топ по
винрейту, фильтры темы 5 — всё это операции над контейнерами, и от выбора контейнера
зависит, будет ли анализатор на 1000 матчей отвечать мгновенно или через секунду.

> **Курс собирается с `-std=c++23` / `/std:c++latest`.** Где приём появился в стандарте —
> помечено в скобках: это важно, когда гуглишь или читаешь чужой код 2015 года.

## Четыре контейнера, которые нужны сейчас

### `std::vector<T>` — ты его уже знаешь

Непрерывный кусок памяти, элементы подряд. Доступ по индексу мгновенный, добавление в конец
дешёвое, поиск по значению — линейный проход.

```cpp
std::vector<ChampionReport> reports;
reports.push_back(std::move(report));   // в конец
reports.size();                         // сколько элементов
for (const ChampionReport& r : reports) { /* ... */ }
```

Берётся по умолчанию. Если не знаешь, какой контейнер нужен, и элементы просто лежат
списком — это `vector`.

### `std::map<Key, Value>` — словарь, упорядоченный по ключу

Пары «ключ → значение», ключи уникальны, элементы всегда отсортированы по ключу.
Внутри — сбалансированное дерево, поиск за `log(n)` сравнений.

```cpp
std::map<std::string, int> games;       // имя чемпиона → число игр

games["Ahri"] = 3;                      // вставить или перезаписать
++games["LeeSin"];                      // если ключа не было — создастся со значением 0, потом ++

auto it = games.find("Zed");            // поиск без вставки
if (it != games.end()) {
    std::println("{} {}", it->first, it->second);   // ключ и значение
}

for (const auto& [name, count] : games) {           // обход по возрастанию ключа
    std::println("{}: {}", name, count);
}
```

**Главная ловушка темы:** `operator[]` **вставляет элемент**, если ключа не было.
Читать через него — значит незаметно менять контейнер:

```cpp
int n = games["Zed"];      // Zed не было — теперь он есть, со значением 0, и size() вырос
```

Инструменты чтения, все — `const`:

```cpp
games.contains("Zed");     // (C++20) true / false — то, что ты и хотел спросить
games.count("Zed");        // 0 или 1 — как это писали до C++20
games.find("Zed");         // итератор или end(), если нужно ещё и значение
games.at("Zed");           // значение или std::out_of_range
```

`contains()` — то, ради чего стоило перейти на новый стандарт в этом месте: он говорит
ровно то, что ты имел в виду, и его нельзя прочитать как «сколько раз». `count()` держи
в голове только для чтения чужого кода и для `multimap`, где ответ бывает больше единицы.

На `const std::map` `operator[]` вообще не скомпилируется, и это защита, а не помеха.

Удаление по условию — одной строкой (C++20), без цикла с `it = m.erase(it)`:

```cpp
std::erase_if(games, [](const auto& kv) { return kv.second < 5; });   // выкинуть редких
```

### `std::unordered_map<Key, Value>` — тот же словарь, но на хеш-таблице

Тот же интерфейс, но порядок обхода произвольный, а поиск в среднем за константу.

```cpp
std::unordered_map<std::string, int> games;   // API почти совпадает с map
```

Быстрее `map` на больших объёмах, но: порядок обхода непредсказуем, и на некоторых
наборах ключей деградирует до линейного. Бери `map`, когда нужен порядок или
детерминированный вывод; `unordered_map` — когда важна только скорость доступа.

### `std::set<T>` — множество уникальных значений

Как `map`, но без значений — только ключи. Отсортировано, дубликаты игнорируются.

```cpp
std::set<std::string> champions;
champions.insert("Ahri");
champions.insert("Ahri");        // второй раз — ничего не произошло, size() == 1
champions.contains("Ahri");      // (C++20) true / false
```

Нужен ровно тогда, когда вопрос звучит «какие уникальные X встречались» — пул чемпионов,
набор ролей, список сыгранных карт.

### `std::flat_map<Key, Value>` — словарь, который внутри вектор (C++23)

Интерфейс `map`, а внутри два отсортированных вектора: ключи и значения. Поиск —
бинарный, `O(log n)`, но по непрерывной памяти; обход — линейный проход по массиву,
а не прыжки по узлам дерева.

```cpp
std::flat_map<std::string, int> games;
games.try_emplace("Ahri", 3);
games.contains("Ahri");
games.keys();                    // весь массив ключей как есть — нет у std::map
```

Плата: **вставка в середину сдвигает хвост вектора**, то есть `O(n)`, и любая вставка
инвалидирует все итераторы. Это точный ответ на «построил один раз — читаю много раз»:
индекс чемпионов строится на старте и дальше только читается. Для таблицы, в которую
сыплются записи по одной, бери `std::map`.

## Стоимость операций — то, ради чего всё это

`n` — число элементов в контейнере.

| Операция | `vector` | `map` / `set` | `unordered_map` | `flat_map` |
|---|---|---|---|---|
| поиск по ключу/значению | `O(n)` | `O(log n)` | `O(1)` в среднем | `O(log n)` |
| вставка | `O(1)` в конец | `O(log n)` | `O(1)` в среднем | `O(n)` |
| обход всех элементов | `O(n)` | `O(n)` | `O(n)` | `O(n)`, по памяти подряд |
| порядок при обходе | порядок вставки | по возрастанию ключа | произвольный | по возрастанию ключа |
| память на элемент | минимум | + узлы дерева | + таблица и корзины | минимум |

Читается это так: на 50 чемпионах разница между `O(n)` и `O(log n)` — это 50 сравнений
против 6. На 100 000 записей это и есть та разница между пятью миллионами операций
и парой сотен тысяч, о которой шла речь в начале.

**Но:** `vector` и `flat_map` на маленьких объёмах часто быстрее `map`, потому что лежат
одним куском в памяти и процессор читает их линейно. «Асимптотически лучше» и «быстрее
на твоих данных» — разные утверждения, и второе проверяется замером, а не рассуждением.
К этому вернёмся в теме 13.

## Поиск по `string_view` без лишней строки

`std::map<std::string, int>` сравнивает ключи через `std::less<std::string>`, и у него
один тип аргумента — `std::string`. Значит `games.find(some_string_view)` не скомпилируется,
а `games.find("Ahri")` тихо **создаст временную `std::string`** — на каждый вызов, включая
вызовы в цикле по ста тысячам записей.

Прозрачный компаратор (C++14 для `map`/`set`, C++20 для `unordered_*`) убирает и то, и другое:

```cpp
std::map<std::string, int, std::less<>> games;   // <> вместо <std::string> — вся разница

std::string_view name = entry.champion_name;
games.contains(name);                             // ищет по view, ничего не выделяя
games.find(name);
```

В сигнатурах задач 4.1–4.3 стоит обычный `std::map<std::string, int>` — так и оставь,
там ищут по имени десятки раз, а не миллионы. Приём нужен, когда ключ ищется в горячем
цикле: тема 12, агрегация по сотням тысяч записей.

## Печать контейнера: `std::print` вместо `std::cout` (C++23)

```cpp
#include <print>

std::println("{}: {}", name, games_count);       // подстановка по {}, без << и без "\n"
std::print("{} игр\n", n);                       // то же самое, перевод строки вручную
std::println("{:>12} | {:.2f}", champion, kda);  // ширина 12 вправо, два знака после точки

std::println("{}", games);                       // {"Ahri": 3, "Zed": 1} — map целиком
std::println("{}", names);                       // ["Ahri", "Zed"] — vector целиком
```

Три причины, почему в новом коде этого курса пишем так, а не `std::cout <<`:

- **форматирование видно одной строкой**, а не собирается из `<<` и `std::setw`;
- **контейнер печатается сам** (C++23) — для отладки индекса это разница между одной
  строкой и циклом;
- **на Windows `std::print` пишет в консоль через `WriteConsoleW`** и не зависит от
  кодовой страницы: русский текст выходит русским, даже когда в консоли cp866.
  `std::cout` в той же консоли отдаёт байты как есть, и получается «ЇаштхЄ».

Ошибка в строке формата (`{}` больше, чем аргументов; `{:.2f}` для `int`) — это ошибка
**компиляции**, а не мусор в выводе: строка формата проверяется в `consteval`.

Тесты по-прежнему на doctest и никакой печати не требуют. `std::println` — для playground
и отладки.

## Перемещение объектов в контейнер

Твоя повторяющаяся ошибка, третий раз подряд. Контейнер хранит **свои** копии элементов:

```cpp
ChampionReport report("Ahri");
reports.push_back(report);              // КОПИЯ: report остаётся валидным и полным
reports.push_back(std::move(report));   // ПЕРЕМЕЩЕНИЕ: содержимое переехало в контейнер
```

Именованная переменная — всегда lvalue, даже в последней строке своей жизни. Компилятор
не умеет догадываться, что она тебе больше не нужна; сказать об этом должен ты, через
`std::move`. Для `map` есть дополнительные способы построить элемент сразу внутри узла:

```cpp
index.emplace(name, ChampionReport(name));      // построить пару на месте
index.try_emplace(name, name);                  // (C++17) вставит, только если ключа ещё нет
index.insert_or_assign(name, report);           // (C++17) вставить или перезаписать значение
```

`try_emplace` — точный ответ на паттерн «найти или создать», который ты писал руками
в задаче 3.3: он не трогает существующий элемент и не создаёт временный объект зря.
Он же возвращает пару `{итератор, вставили ли}` — то есть заменяет связку
«проверил `contains`, потом вставил» одним поиском вместо двух.

## Пять ошибок этой темы

| Что сделал | Что увидишь |
|---|---|
| прочитал значение через `operator[]` | ничего при компиляции; контейнер тихо вырос, `size()` не тот, в выводе появились чемпионы с нулём игр |
| `operator[]` на `const std::map` | `C2678` / `error: no viable overloaded operator[] on const map` — компилятор спас |
| сохранил итератор и изменил контейнер | у `vector` и `flat_map` — ASan `heap-use-after-free` после вставки; у `map` — итераторы выживают, кроме удалённого элемента |
| сравнил `it` с `end()` после `erase` | UB: итератор повис; `erase` возвращает следующий валидный — им и пользуйся (а ещё лучше `std::erase_if`) |
| положил в контейнер без `std::move` | ничего, кроме лишней копии; на `ChampionReport` со строкой и вектором внутри это заметно |

Третья и четвёртая — единственные в этой теме, которые ловятся только санитайзером.
Первая — самая частая и самая тихая: её не поймает ни компилятор, ни ASan, только тест.

## Читать в книгах

- **«Грокаем алгоритмы», глава 1 (бинарный поиск).** Почему `log n` — это так мало.
  Именно бинарный поиск объясняет, откуда у `map` берётся `O(log n)`: дерево делит
  диапазон пополам на каждом шаге, ровно как поиск в отсортированном массиве —
  и `flat_map` делает буквально второе.
- **«Грокаем алгоритмы», глава 2 (массивы и связанные списки).** Разница между
  «лежит подряд» и «лежит по ссылкам» — это и есть разница между `vector` и `map`
  по памяти и по скорости обхода.
- **«Грокаем алгоритмы», глава 5 (хеш-таблицы).** Ровно про `unordered_map`: как из ключа
  получается индекс, что такое коллизия и почему «в среднем `O(1)`» — со звёздочкой.
- **«Грокаем алгоритмы», главы 7 и 8** — по диагонали, они про графы и жадные алгоритмы;
  вернёмся к ним в теме 13. Сейчас достаточно 1, 2 и 5.
- **«Чистый код», глава 17, раздел G — «Границы».** Не выставляй наружу тип контейнера,
  если можешь выставить операцию. `ChampionNames()` лучше, чем публичный `std::map`:
  внутренность можно поменять — хоть на `flat_map` — не сломав вызывающих.

> Сверь номера глав со своим изданием при первом обращении — в русских переводах
> нумерация иногда съезжает.

Алгоритмы над этими контейнерами — `std::ranges::sort`, `views::filter`, проекции,
`ranges::to` — это тема 5 целиком. Здесь контейнеры только заполняются и читаются.

## ВЫПИСАТЬ В БЛОКНОТ

```
ВЫБОР КОНТЕЙНЕРА
  просто список, порядок вставки .......... std::vector
  ключ → значение, нужен порядок .......... std::map
  ключ → значение, нужна скорость ......... std::unordered_map
  только уникальные значения .............. std::set
  построил один раз, читаю много .......... std::flat_map   (C++23)

СТОИМОСТЬ (n — размер контейнера)
  vector:         поиск O(n),     вставка в конец O(1)
  map / set:      поиск O(log n), вставка O(log n),  обход по возрастанию ключа
  unordered_map:  поиск O(1)*,    вставка O(1)*,     порядок обхода произвольный
  flat_map:       поиск O(log n), вставка O(n),      память подряд, есть keys()
  * в среднем; в худшем случае деградирует до O(n)

MAP: ЧТЕНИЕ И ЗАПИСЬ — РАЗНЫЕ ОПЕРАЦИИ
  m[key]                 вставит элемент, если ключа не было!  только для записи
  m.contains(key)        true / false            (C++20)       для проверки
  m.find(key)            итератор или m.end()                  для чтения
  m.at(key)              значение или исключение               для чтения
  it->first / it->second ключ / значение
  for (const auto& [k, v] : m)   обход

ВСТАВКА И УДАЛЕНИЕ БЕЗ ЛИШНЕЙ РАБОТЫ
  v.push_back(std::move(x))       именованная переменная — всегда lvalue
  m.try_emplace(key, args...)     (C++17) «найти или создать» одним поиском,
                                  существующий элемент не трогает
  m.insert_or_assign(key, v)      (C++17) вставить или перезаписать
  std::erase_if(m, pred)          (C++20) удалить по условию без цикла с итераторами

ПОИСК БЕЗ ЛИШНЕЙ СТРОКИ
  std::map<std::string, int, std::less<>>   ключ ищется по string_view,
                                            временная std::string не создаётся

  std::println("{}", games)            печатает весь map / vector
  ошибка в "{}" — ошибка компиляции, не мусор в выводе

                      // компилятор молчит, ASan молчит, ловит только тест
```
